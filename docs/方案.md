# Visual Terrain Block — 悬空地形块

> 目标：让玩家贴着墙面/空中**任意延伸地形块**，而不是像原版那样几个就被拦。
> Mod Id：`Jove.VisualTerrainBlock`　最低游戏版本：1.1.0.0

---

## 0. 问题溯源（源码实证）

原版地形块 `TerrainBlock` 的方块规则其实已经是 `MatterBelow: "Any"`（不要求下方有东西），
真正限制水平延伸的是另外四道规则：

| # | 规则 | 位置 | 玩家看到的现象 |
|---|---|---|---|
| 1 | 方向顺序：必须等"后方"的地形块完工 | `Timberborn.Terraforming.TerraformingDirectionalBlocker` | 工地状态「此工程正等待后方的工程完成。」 |
| 2 | 垂直顺序：必须自下而上 | 同上 | 「此工程正等待下方的工程完工。」 |
| 3 | 放置/施工时的物理支撑校验 | `GroundRaisingService.ValidateConstructionSite` → `PhysicallySupportedConstructionSite.Validate` → `ITerrainPhysicsService.CanTerrainBeAdded` | 拉到几块后预览变红、放不下去 |
| 4 | 载入时清理无支撑结构 | `TerrainPhysicsPostLoader.Validate()` → `RemoveBlockObjects()` / `RemoveTerrain()` | 读档后悬空物消失，日志「地形的支撑无效，已被删除。」 |

地形本身是**每体素一个 bool**（`TerrainMap` 里的 `PackedList<bool>`），所以"悬空地形体素"在数据上存得下，
限制全部来自上面四条玩法规则，而不是数据结构。

---

## 1. 三阶段方案

| 阶段 | 内容 | 目的 |
|---|---|---|
| **L1（已实现）** | 新建筑 `VisualTerrainBlock`：外观=原版地形块，`MatterBelow: Any`，去掉 `TerrainPhysicsBlockObjectValidatorSpec`、不加 `GroundRaiserSpec` | 先验证"能不能拖出长条、能不能悬空放置" |
| **L2** | 蓝图加回 `"GroundRaiserSpec": {}`（一行），完工后走原版逻辑：删方块 + `ITerrainService.SetTerrain(coords, 1)` | 变成**真地形** → 可挖、可种树、挡水自动成立 |
| **L3（Harmony）** | a) 放宽 `CanTerrainBeAdded` / `ValidateConstructionSite`<br>b) 让 `TerrainPhysicsPostLoader` 跳过我们生成的坐标 | 让 L2 的悬空地形能放置、读档不被删 |

## 2. L1 实现（当前仓库内容）

```
Buildings/Landscaping/VisualTerrainBlock/VisualTerrainBlock.blueprint.json   ← 建筑蓝图在 mod 根目录

```

> ⚠️ 踩坑：建筑蓝图**不能**放在 `Blueprints/` 目录下。`Blueprints/` 只用于 `TemplateCollections`，
> 其它蓝图目录（`Buildings/`、`Goods/`、`Recipes/`…）必须直接放在 mod 根目录。
> 放错位置时游戏在启动阶段就抛
> `ArgumentException: Blueprint not found at path: Buildings/.../X.blueprint`
> （`TemplateCollectionService.Load` → `SpecService.GetBlueprint`），整个游戏起不来。

关键字段与意图：

| 字段 | 值 | 原因 |
|---|---|---|
| `BlockObjectSpec.Blocks[0].MatterBelow` | `"Any"` | 不要求下方支撑 |
| `...Occupations` | `"All"` | 可站人、可按地形方向使用 |
| `...Stackable` | `"BlockObject"` | 允许在它上面继续叠方块/建筑（`GroundOrStackable` 类） |
| `TerrainPhysicsBlockObjectValidatorSpec` | **不写** | 关掉放置时的物理支撑校验 |
| `GroundRaiserSpec` | **不写（L1）** | 保持普通建筑方块，不转成地形 |
| `PlaceableBlockObjectSpec.ToolGroupId` | `"Landscaping"` | 和原版地形块同一个工具组，`ToolOrder` 110 |
| `BuildingSpec.BuildingCost` | 4 泥土 | 与原地形块一致 |
| `BuildingSpec.ScienceCost` | 1000 | 与原地形块一致；调试时想免科研可改 0 |
| `Children.#Finished.TimbermeshSpec.Model` | `Buildings/Landscaping/TerrainBlock/TerrainBlock.Finished.Model` | 直接复用原版模型，外观 100% 一致 |

部署：`tools/deploy.sh` 会把内容同步到 `~/Documents/Timberborn/Mods/VisualTerrainBlock`。

## 3. 验证（L1 验收）

1. 重启游戏，模组列表里应出现 **Visual Terrain Block (v0.1.0)**，默认启用。
2. 进入存档，在**地形改造**工具组里应多出「悬空地形块」（科研需求同原版地形块）。
3. 贴着悬崖侧面水平拖一串：
   - **能拖超过 3 块、不出现"等待后方的工程完成"** → 第 1 条规则被绕开 ✅
   - **不会有红框/无法放置提示** → 第 3 条规则被绕开 ✅
4. 用开发者模式（⌥⇧Z）快速完成施工，检查：
   - 方块外观与地形块一致
   - 能在上面继续叠方块、能站人走

### 已知风险（L1 阶段必然会遇到的）

- **可达性**：普通建筑需要工人有路可达工地。悬空太远的位置会显示「无法到达」，方块永远建不完——
  这不是放置限制，是施工限制。先确认"能放下"，可达性问题留到 L2/L3 再处理。
- **水/树/挖掘**：L1 是纯视觉方块，水会穿过、树不能种、只能拆不能挖。这三项要等 L2 变成真地形。

### 实测记录：载入时被清理（v0.1.0 → v0.1.1 修复）

第一次实测结果：**放置和施工都正常**（能悬空拉出一长串，物理校验没有拦），但读档时弹窗：

```
载入问题
· 对象位置无效，已被删除：悬空地形块。(9)
· 对象位置无效，已被删除：道路。(9)
```

对应 `LoadingIssue.BlockObjectLoadingIssue`，即 `TerrainPhysicsPostLoader` 的载入清理：

```
ValidateAll() → Validate() → RemoveBlockObjects() / RemoveTerrain()
RemoveBlockObjects：遍历 EntityRegistry.Entities，
  凡是不在内部白名单 _validBlockObjects（HashSet<BlockObject>）里的方块 → 删除并报载入问题
_validBlockObjects 由 GetInitialCandidates() 从地图底部逐列 BFS 填充，悬空方块永远进不去
```

所以"无支撑"本身不是问题，**"没有被 BFS 认领"才是问题**。

**v0.1.1 的修法（最小侵入）**：

1. 蓝图加 `"VisualTerrainBlockMarkerSpec": {}` → 每个悬空地形块实体带上 `VisualTerrainBlockMarker` 标记组件。
2. Harmony prefix 打在 `TerrainPhysicsPostLoader.RemoveBlockObjects` 上，执行前把所有带标记的方块
   塞进 `_validBlockObjects`，然后照常跑原方法 —— 我们的方块免删，其它对象的校验逻辑一点不动。

选择这个 hook 而不是整体跳过 `Validate()` 的原因：跳过会让 `ValidateAll()` 走到 `Enable()`，
把 `TerrainPhysicsValidationEnabler` 打开，之后的放置又会开始做物理校验，反而把功能废掉。

代码：`src/LoadCleanupPatch.cs`、`src/VisualTerrainBlockMarker.cs`；
Harmony 由 workshop 的 Harmony mod 提供（`manifest.json` 里 `RequiredMods` 声明，不随本 mod 分发）。

> ⚠️ ComponentSpec 是 C# `record`，netstandard2.1 下要补一个
> `namespace System.Runtime.CompilerServices { internal static class IsExternalInit {} }` 才能编译。

**L2（一行改动）**：在 blueprint 里加回 `"GroundRaiserSpec": {}`，
完工后由 `GroundRaisingService.OnEntityDeleted` 调 `SetTerrain(coords, 1)` 变成真地形。

**L3（Harmony 补丁）**：

| 目标 | 方法 | 处理 |
|---|---|---|
| 放置校验 | `Timberborn.ConstructionSites.PhysicallySupportedConstructionSite.Validate` 或 `ITerrainPhysicsService.CanTerrainBeAdded` | L1 实测未被拦截（已删 `TerrainPhysicsBlockObjectValidatorSpec`），L2 加上 `GroundRaiserSpec` 后若被拦再补 |
| 载入清理 | `TerrainPhysicsPostLoader.RemoveBlockObjects` | ✅ v0.1.1 已做，方块免删；L2 转成真地形后还需要处理 `RemoveTerrain` 对悬空地形的清理 |
| 方向/垂直顺序 | `TerraformingDirectionalBlocker` 的状态 | 我们的方块没有这个组件，天然不触发 |

**必须验证的边界**（L2 之后）：

- 读档后悬空地形是否存活（`Player.log` 不应出现「地形的支撑无效，已被删除」）
- 悬空地形上的水流动是否正常（会不会从下方缝隙漏）
- 悬空地形上种树、放建筑是否合法（`MatterBelow.Ground` 满足）
- 挖掘工具能否正常挖掉悬空地形、是否会连带删除下方方块
- 存档在**未安装本 mod** 的客户端打开会怎样（未知蓝图）

## 5. 拆除与炸药（v0.1.5）

### 怎么拆掉悬空地形块

- **拆除工具**：方块是普通建筑（`Deconstructible`），框选即删，不需要工人、不检查支撑。
- **炸药**：v0.1.5 之前放不上——原版 `Dynamite` 的 `MatterBelow` 是 `Ground`（必须脚下是真地形），
  悬空块上会提示「下方地面缺失」。

### v0.1.5 的两处改动

| 改动 | 做法 |
|---|---|
| 炸药能放在悬空块上 | 覆盖 `Dynamite` / `DoubleDynamite` / `TripleDynamite` 三个蓝图（两阵营共 6 个文件），`MatterBelow` 从 `Ground` 改成 `GroundOrStackable`：真地形满足 Ground，我们的方块（`Stackable: BlockObject`）满足 Stackable |
| 爆炸真的能炸掉方块 | `Dynamite.Detonate` 只做三件事（降地形 / 删脚下的道路 / 炸死海狸），不删建筑。补一个 postfix：爆点切比雪夫距离 ≤1 范围内名字以 `VisualTerrainBlock` 开头的方块一并 `EntityService.Delete` |

> `MatterBelowValidator` 的枚举：`Ground`（脚下有地形）、`GroundOrStackable`（地形或可堆叠方块）、
> `Air`、`Any`、`Stackable`。选 `GroundOrStackable` 而不是 `Any`，是为了只放开"有东西托着"的情况，
> 维持原版不让炸药凭空悬着的约束。

## 6. 只能往上叠、不能往旁边伸（v0.1.6）

现象：方块能叠在上面（黄色预览），往旁边伸进空气里就是红的，放不下去。

根因：**放置阶段的物理支撑校验是全局的，不挂在蓝图 spec 上**。
删掉 `TerrainPhysicsBlockObjectValidatorSpec` 只绕过"落地"那一层，光标预览走的是另一条路：

```
放置工具（Application 程序集）→ ITerrainPhysicsService.ValidateBlockObjectPreview(BlockObject)
```

- 叠在已有方块上 → 下方有东西 → 校验通过 → 黄色
- 往旁边伸进空气 → 无支撑 → 校验失败 → 红色

修法（`src/PlacementPatch.cs`）：

| 目标 | 处理 |
|---|---|
| `TerrainPhysicsService.ValidateBlockObjectPreview(BlockObject)` | prefix：预览对象名以 `VisualTerrainBlock` 开头 → 直接 `true` |
| `TerrainPhysicsService.CanBeDestroyed(BlockObject)` | prefix：我们的方块返回 `false`，避免炸药/挖掘改变地形时被物理系统顺手删掉 |

识别依旧用 `BlockObject.Name` 前缀（预览对象名同样以 `VisualTerrainBlock` 开头）。

## 7. L2 落地：完工转真地形（v0.2.0）

### 为什么"侧面吸不住"不是补丁能解决的

光标幽灵的落点由 `Timberborn.BlockObjectPickingSystem.BlockObjectPreviewPicker.CenteredPreviewCoordinates` 决定，
它只认两种锚点：

- **地形**：`ITerrainService.Contains(coords.XY)` 命中后走 `ComposeCoordinates(face)`，按你指的**面**偏移一格
- **可堆叠方块的上表面**：`IsTerrainOrStackable(coords)` 命中后抬到上一格

而方块对象想当"墙"时，`ShouldObjectBlockCoordinates(block, coords)` 会返回 false（它要求 `Block.Occupation.IsFull()`
且 `DoesBlockAboveHasFullOccupation` 成立），于是射线**直接穿透**这个方块，最后打到它背后的地形 —— 幽灵跳到地面层。
这就是"指侧面吸不住、也没有警告文字"的原因：不是校验拒绝，而是拾取阶段根本没算到那一格。

结论：方块对象永远当不了地形那样的锚点，只能走 L2 —— **让方块完工后变成真地形**。

### v0.2.0 的三处改动

| 改动 | 内容 |
|---|---|
| 蓝图加 `GroundRaiserSpec: {}` | 复用原版地形块的机制：完工时 `GroundRaisingService.OnEntityDeleted` 删掉方块 + `ITerrainService.SetTerrain(coords)` |
| `Stackable` 改回 `UnfinishedGround` | 与原地形块一致（原来是 `BlockObject`，属于自定义值） |
| 补丁 `TerrainPhysicsService.CanTerrainBeAdded(Vector3Int)` → true | `PhysicallySupportedConstructionSite.Validate` 的实现就是 `IsValid = CanTerrainBeAdded(coords)`，一个开关同时放开"悬空位置能生成地形"和"建成后合法" |

`MatterBelow` 保持 `Any`（原版地形块也是），这样施工阶段可以先悬空放工地。

### 收益

变成真地形之后，之前那三条需求自动成立：

- **可挖**：挖掘工具作用在地形体素上
- **挡水**：地形本身就是水体素边界
- **可种树**：`MatterBelow.Ground` 满足
- **可对齐**：贴着已建成地形拖动时走 `terrain` 分支，按格对齐（和贴悬崖一样）

### 注意

- 存档里 **v0.2.0 之前放的方块不会自动转换**，仍是方块对象；需要拆掉重放（或后续加一次性迁移逻辑）。
- 载入时的地形清理已被 `TerrainPhysicsPostLoader.Validate` 拦截（见第 3 节），悬空地形不会被 "无支撑" 删掉。
